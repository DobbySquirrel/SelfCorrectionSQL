# CoCTE-MCTS 框架说明

## 核心思想

**CoCTE（Cumulative Common Table Expression）**：通过**逐步累积**的方式构建 SQL，每一步只生成一个 CTE delta，而不是一次性生成完整 SQL。

## 工作流程

### 1. **Multi-Strategy 并行探索**
- 对每个问题，**并行运行 4 个策略**（S1/S2/S3/S4）
- 将总 rollout 预算（默认 40）**平均分配**给 4 个策略（每个策略 10 个 rollout）
- 最后从 4 个策略结果中选择最优的（优先级：无错误 > SQL 非空 > score 最高）

### 2. **MCTS 树搜索**
每个策略独立运行 MCTS：
- **Selection**：使用 UCT 算法选择节点（如果节点子节点未满，优先扩展该节点）
- **Expansion**：生成新的动作（PROBE/BUILD/REFINE/FINISH）
- **Evaluation**：执行动作，计算自一致性奖励（Self-Consistency Score）
- **Backpropagation**：将奖励回传到路径上的所有节点

### 3. **四种动作类型**

| 动作 | 用途 | 输出格式 |
|------|------|----------|
| **PROBE** | 探测数据库信息（列值分布、连接有效性等） | JSON 工具调用列表 |
| **BUILD** | 添加新的 CTE | `<cte_name> AS (...)` |
| **REFINE** | 修正最后一个 CTE（修复错误） | `<cte_name> AS (...)`（同名替换） |
| **FINISH** | 完成查询，生成最终 SELECT | `SELECT ...` |

### 4. **四种策略**

| 策略 | 特点 | 适用场景 |
|------|------|----------|
| **S1 (Entity-First)** | 实体优先，先探测实体值再构建 | 需要过滤特定实体值的问题 |
| **S2 (Relation-First)** | 关系优先，先验证连接再构建 | 涉及多表连接的问题 |
| **S3 (Proactive)** | 主动策略，有足够证据时直接构建 | 问题明确、证据充分 |
| **S4 (Reactive)** | 被动策略，依赖执行反馈 | 问题复杂、需要试错 |

### 5. **自一致性评估（Self-Consistency）**

- 每次生成 `k_samples` 个候选（默认 1，建议 3-5）
- 通过**多数投票**决定动作类型
- 执行候选，计算**结果一致性**作为奖励
- 选择结果最一致的候选作为代表

## 关键参数

```python
max_rollouts = 10          # 每个策略的 rollout 次数
max_depth = 8              # MCTS 树最大深度
k_samples = 1               # 每次生成的候选数量（建议 3-5）
max_children_per_node = 2   # 每个节点最多扩展 2 个子节点
```

## 可能的问题

### 1. **准确度低的可能原因**

1. **k_samples 太小**（当前为 1）
   - 问题：无法通过多数投票过滤错误候选
   - 建议：增加到 3-5

2. **rollout 预算分配不均**
   - 问题：每个策略只有 10 个 rollout，可能不够探索
   - 建议：增加总预算或减少策略数量

3. **自一致性评估不够严格**
   - 问题：可能选择了语法错误但结果一致的 SQL
   - 建议：在评估时过滤掉无效 SQL

4. **策略选择逻辑简单**
   - 问题：只按 score 选择，可能忽略了其他因素
   - 建议：考虑 SQL 复杂度、执行时间等因素

### 2. **与 mcts_v1 的差异**

| 特性 | mcts_v1 | mcts_v2 |
|------|---------|---------|
| CTE 生成方式 | 一次性生成多个 CTE 变体 | 逐步累积，每次一个 CTE delta |
| 策略使用 | LLM 选择或固定策略 | 并行运行 4 个策略，选择最优 |
| 动作类型 | 只有 BUILD | PROBE/BUILD/REFINE/FINISH |
| 错误处理 | 创建失败节点 | REFINE 动作修正 |
| 自一致性 | 基于 SQL 变体结果一致性 | 基于动作候选结果一致性 |

## 优化建议

1. **增加候选数量**：`k_samples = 3-5`，提高多数投票的可靠性
2. **增加 rollout 预算**：每个策略至少 15-20 个 rollout
3. **改进选择逻辑**：在 `select_best_result` 中考虑更多因素（SQL 长度、执行时间等）
4. **添加 SQL 验证**：在选择前验证 SQL 语法和执行有效性
5. **动态策略分配**：根据问题复杂度动态分配 rollout 预算，而不是平均分配
